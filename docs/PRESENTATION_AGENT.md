# PRESENTATION_AGENT · HTML 발표자료 공통 제작 규칙

정착 경로: `docs/PRESENTATION_AGENT.md` / 버전: 1.0.0

이 규칙은 회차별 내용과 분리된 공통 디자인·교육·검수 기준이다. 값이 바뀌면 CSS 토큰, 템플릿, QA 기대값을 함께 수정한다. 과거 강의의 내용까지 자동으로 바꾸지 않는다.

## 1. 역할과 판단 기준

발표자료 제작자는 원문을 슬라이드에 옮기는 편집자가 아니라, 청중이 이해할 수 있도록 근거와 설명 순서를 설계하는 역할이다. 단, 해석이나 설명용 예시를 원저자의 주장·실험 결과처럼 포장하지 않는다.

현재 강의 설정에서 시간, 청중, 발표자 배경, 언어, 목표 장수, 원본 자료, 참고 PPT, 꼭 포함할 항목, 제외 항목을 읽는다. 미지정 항목은 목적에 맞게 판단하되 이미 주어진 일정·실습 없음 등의 조건을 다시 질문하지 않는다.

교육용 강의의 기본 청중은 AI Agent 사용 경험이 많지 않은 대학생이다. 발표자는 로봇·회로·AI 프로젝트 경험이 있으나 소프트웨어·보안 분야 모든 세부사항을 알고 있다고 가정하지 않는다.

## 2. 발표 모드

- `source_faithful`: 논문·보고서 중심. 원본의 논리·주장·핵심 Figure·표·수식·Algorithm을 유지한다.
- `research_synthesis`: 여러 공식 문서를 묶는 교육. 교육 목표에 맞춰 순서를 새로 설계하되 출처별 주장과 확인일을 추적한다.
- `mixed`: 원문·공식 문서·사용자 경험·실험을 조합. 각각을 명확히 구분한다.

기본적인 설명 구조는 문제/목적 → 배경 → 핵심 개념 → 방법/시스템/과정 → 필요한 분석 → 근거/결과 → 한계/적용이다. 수식·Algorithm·실험 결과가 없는 자료에 이를 억지로 추가하지 않는다.

동아리 강의에서는 “왜 필요한가 → 익숙한 사용 방식과 무엇이 다른가 → 어떻게 쓰는가 → 주의할 점 → 발표자의 경험”을 상황에 맞춰 사용한다. 원본 발표자료를 참고해도 페이지 배치를 기계적으로 복사하지 않는다.

## 3. 내용 구성과 분량

한 슬라이드는 하나의 핵심 메시지를 가진다. 제목만 순서대로 읽어도 설명의 흐름이 보여야 한다. 제목은 단순 용어 나열보다 그 장에서 전달할 관계·결론을 담는다. 다만 강한 인과나 성능 우위를 근거 없이 제목에 넣지 않는다.

보조 설명은 필요한 만큼만 넣고 보통 2–5개 이내로 제한한다. 3–5개를 의무적으로 채우지 않는다. 큰 Figure나 한 문장이 주인공인 장은 그것으로 충분하다. 긴 문단, 10개 이상의 나열, 모든 슬라이드의 동일한 4개 카드 구성을 피한다.

장수보다 정확성과 가독성을 우선하되 사용자가 정확한 장수를 지정하면 내용 압축·부록 이동으로 맞춘다. 핵심 내용을 뺄 수 없어 목표를 못 맞추는 경우 숨기지 말고 사유와 실제 장수를 보고한다. 1회차 기본 목표는 본편 30장이고 부록은 별도 집계한다.

회차 설정의 전체 시간과 고정 질의응답 배정을 읽어 발표 시간을 계산한다. 기본 언어는 한국어이며, 회차별 명시 설정이 있으면 그 언어를 따른다. 고정 질의응답은 회차에 명시된 값으로 집계하고, 유동 운영에서는 0분으로 두며 진행 중 또는 실제 남는 시간에 질문을 받는다. 원고와 전환의 목표 시간은 리허설 전 추정치다. ‘학습용 해설’을 읽는 시간에 포함하지 않는다.

## 4. 언어와 용어

회차별 언어 설정이 최우선이다. 별도 설정이 없으면 슬라이드와 발표 원고 모두 한국어다. 명시적 회차 설정으로 다른 언어를 사용할 수 있다. 제목·본문·표·도식·주석·목차·포트폴리오 설명을 실제로 해당 언어로 작성하고, 설정 필드만 바꿔 완료 처리하지 않는다. 처음 등장하는 전문용어에는 짧은 한국어 의미를 병기할 수 있다. Figure 원문·고유명·제품명·코드·경로·URL·실제 UI 문구는 정확히 유지하고 필요한 한국어 설명을 덧붙인다.

회사·모델·서비스·하네스·표준·Skill 형식은 같은 범주처럼 섞지 않는다. 예를 들어 회사와 제품을 동일한 비교 열에 무분별하게 놓지 않는다. `Agent AI`와 `AI Agent`는 처음에 관계를 설명하고 본문에서는 `AI Agent`를 기본 표기로 통일한다.

MCP·Skill·하네스의 비유는 이해를 위한 설명이다. 비유와 기술적 정의가 완전히 동일하다고 말하지 않는다. 제품별 Skill 지원·구조가 다르면 그 차이를 검증해 한정한다.

## 5. 디자인 토큰 · 반드시 코드로 고정

### 5.1 논리 캔버스와 축척

논리 슬라이드는 **1920×1080**이다. 고정 캔버스 내부의 위치·크기를 유지하고 화면에는 전체를 같은 비율로 축소한다.

```text
scale = min(사용 가능한 화면 너비 / 1920, 사용 가능한 화면 높이 / 1080)
```

헤더·툴바 높이를 빼고 계산하고, canvas를 담는 stage를 중앙 정렬한다. 슬라이드 내부를 viewport마다 다른 열 배치로 바꾸지 않는다. 포트폴리오 목록은 별도로 반응형으로 만든다.

1920px 논리 좌표의 40px는 1280px 화면에서는 약 26.7px로 보인다. 따라서 작은 웹 본문 글자 크기를 그대로 가져오지 않는다. 이전 대화의 `1920px 본문 24–27px` 제안은 이 최종 규칙에서 사용하지 않는다.

PPTX를 13⅓×7½인치로 내보내면 가로 폭은 960pt다. 비율을 유지한 논리 글자 64px는 해당 슬라이드에서 약 32pt에 해당한다. CSS 절대단위의 `1px = 0.75pt`만 적용해 축소 후 발표 글자 크기를 계산하지 않는다.

### 5.2 기본 글꼴

본문·제목·숫자·차트·표는 **Pretendard**의 Regular 400, SemiBold 600, Bold 700을 기본 사용한다. 기본 배포에서 임의로 시스템 고딕으로 바뀌면 QA 실패다. fallback은 사용자 미리보기의 복구용이지 완성본의 허용 기준이 아니다.

```css
:root {
  --font-sans: "Pretendard", "Noto Sans KR", "Apple SD Gothic Neo", "Malgun Gothic", sans-serif;
  --font-mono: "JetBrains Mono", "D2Coding", "Pretendard", monospace;
  --slide-width: 1920px;
  --slide-height: 1080px;
  --font-title-cover: 88px;
  --font-title: 64px;
  --font-lead: 48px;
  --font-body: 40px;
  --font-secondary: 32px;
  --font-caption: 28px;
  --font-footer: 24px;
  --font-code: 32px;
  --safe-x: 104px;
  --safe-top: 64px;
  --safe-bottom: 52px;
  --text-primary: #111111;
  --text-secondary: #555555;
  --text-muted: #616161;
  --background: #FFFFFF;
  --line: #E5E5E5;
  --panel: #F7F7F7;
  --accent: #2657C8;
}
```

수식은 KaTeX가 사용하는 수학 글꼴과 CSS를 같은 고정 버전으로 가져온다. 코드의 한글 주석은 가짜 고정폭 정렬에 의존하지 않게 한다. 코드를 그림으로 만드는 것보다 실제 텍스트로 보여주는 것을 우선한다.

이 프롬프트 팩 자체에는 글꼴 바이너리가 없다. 구현 시 공식 출처의 의존성으로 사용자 환경에 설치·확보하고, 버전·해시·필요 고지를 관리한다. 운영체제의 임의 폰트 파일을 복사해 저장소나 배포물에 넣지 않는다. [R06]

웹폰트는 `@font-face`로 로컬 자산을 읽는다. release에서는 CDN-only fallback을 두지 않는다. `document.fonts.ready`와 실제 필요한 font face의 로딩 성공을 확인한 뒤 Chart.js·Mermaid·캡처를 실행한다. `font-family` 문자열만 설정한 것으로 폰트 로딩 성공을 판단하지 않는다.

### 5.3 크기와 밀도

| 요소 | 기본 크기 | 규칙 |
|---|---:|---|
| 표지 제목 | 88px | 너무 길면 문장을 줄이거나 부제 분리 |
| 일반 제목 | 64px | 최대 2줄; 제목 영역은 일정하게 확보 |
| 핵심 메시지 | 48px | 짧은 문장 1–2개 |
| 본문 | 40px | 일반 본문은 36px 미만으로 내리지 않음 |
| 보조 설명 | 32px | 핵심 내용의 대체가 아님 |
| 캡션·차트 작은 라벨 | 28px | 설명해야 하는 라벨은 가급적 32px |
| 출처·페이지 번호 | 24px | 장식으로 흐리게 숨기지 않음 |
| 코드 | 32px | 28px 미만 금지; 길면 부분 발췌·슬라이드 분리 |

본문 줄간격은 1.35–1.5, 제목은 1.15–1.25 범위다. 제목 높이는 최대 두 줄과 간격을 고려해 공통 영역으로 예약한다. 본문 공간 부족을 무작위 글자 축소·여백 삭제로 해결하지 않는다.

### 5.4 여백과 하단

좌우 104px, 상단 64px, 하단 52px를 기본 안전 여백으로 둔다. 제목 영역과 콘텐츠 사이, 콘텐츠와 하단 출처 사이에 최소 24–32px를 확보한다. footer에는 강의 식별자, 출처 ID, 페이지 번호를 일관되게 배치한다.

모든 페이지가 동일한 장식 레이아웃일 필요는 없지만 제목 시작 좌표·footer 기준선·안전 여백은 유지한다. 큰 이미지도 축·범례·단위가 안전 영역 밖으로 나가지 않게 한다.

### 5.5 색상과 이미지

흰색 배경, 검정·진한 회색 본문이 기본이다. 강조는 굵기·위치·밑줄·테두리·번호를 먼저 사용한다. 색상은 그래프·공식 이미지 해석이나 하나의 강조 대상에 필요한 만큼만 쓴다. 그라데이션, 배경 패턴, 장식용 아이콘, 의미 없는 큰 배경 사진은 사용하지 않는다.

색 하나만으로 구분하지 않는다. 차트는 마커·선 패턴·직접 라벨도 사용한다. 회색 범례가 너무 비슷해 구분되지 않으면 제한적인 색 사용을 허용한다. 회사 로고 색은 필요할 때 보존하되 페이지 전체를 브랜드색으로 채우지 않는다.

## 6. 레이아웃 종류

템플릿의 목록은 제한하되, 콘텐츠에 맞게 선택한다.

| 레이아웃 | 적합한 내용 |
|---|---|
| `cover` / `section` | 강의 시작과 큰 주제 전환 |
| `statement` | 중요한 문장 하나·오해 바로잡기 |
| `text-figure` | 설명 + 실제 Figure나 UI |
| `figure-focus` | 큰 Figure·차트와 짧은 읽기 안내 |
| `screenshot` | 사용자 승인 원본 화면 전체를 픽셀 수정 없이 한 장에 표시 |
| `comparison` | 같은 기준으로 보는 2–3개 대상 |
| `process` | 순서·의사결정·도구 연결 |
| `table` | 정밀 수치·요금·조건 비교 |
| `code-prompt` | 잘못된 프롬프트와 개선 예시 |
| `case-study` | 실제 문제·사용자 선택·AI 역할·검증 |
| `summary` / `qa` | 핵심 회수·질의응답 |

동일 카드 템플릿을 전체에 반복하지 않는다. 4개 이상의 회사를 좁은 열에 동시에 넣는 대신 비교 축을 나누거나 여러 장으로 분리한다. 레이아웃 선택은 `deck.json`에 기록해 임의 raw HTML 없이도 구현 가능하게 한다.

## 7. Figure·표·도식

원본의 핵심 Figure·표·Diagram·Algorithm·사례는 내용 커버리지 표에 등록한다. 원본에 없는 수치·결론·인과를 추가하지 않는다. 복잡한 그림을 줄일 때도 축·범례·단위·핵심 캡션을 보존한다.

이미지는 `object-fit: contain`을 기본으로 하고 종횡비를 유지한다. 주변 불필요한 여백을 자르는 것은 허용하지만 설명에 필요한 요소를 자르지 않는다. crop·재구성·번역한 경우 자산 기록에 변경 사항을 남긴다.

화면에는 “이 그림에서 볼 것”을 짧게 넣고 대본에는 시선 이동 순서를 쓴다. 표가 작아지면 핵심 행·열을 분리한다. 선택적으로 행을 뺐으면 원본 전체 결과인 것처럼 표현하지 않는다.

출처 표기를 구분한다.

- 원본 그대로: `출처: 기관, 자료명, 그림/페이지, 확인일`.
- 의미를 유지해 단순화: `… 자료를 바탕으로 재구성` 또는 `… 자료를 단순화`.
- 여러 자료를 종합한 설명도: `설명용 도식 · 참고 자료: …`.
- 사용자 경험: `발표자 경험 · 적용 환경/시기`; 검증하지 않은 일반 성능 주장으로 확대하지 않음.
- 수치 예시: `설명용 가상 데이터 · 실제 성능 결과 아님`.

출처를 썼다는 이유만으로 재배포 가능하다고 판단하지 않는다. 재사용 권한이 불명확한 인터넷 밈·스크린샷·논문 전체는 공개 패키지에 넣지 않는다.

## 8. Chart.js 규칙

수치 데이터가 설명에 도움이 되는 경우만 사용한다. 회사의 ‘똑똑함’, ‘코딩력’, ‘가성비’를 근거 없는 5점 척도·레이더 그래프로 만들지 않는다. 요금과 API 가격은 단위·통화·과금 모델이 다르면 하나의 막대로 비교하지 않는다.

### 8.1 데이터와 의미

데이터는 `charts/<chart-id>.json` 같은 독립 파일로 둔다. 원천 출처, 조건, 단위, 수집/확인일, 원시값, 가공식, 결측 처리, 표시한 항목을 기록한다. 데이터 없는 값을 0으로 바꾸지 않는다.

막대는 기본적으로 0 기준선을 사용한다. 축을 자르거나 로그축을 쓰면 왜 필요한지와 축 형태를 명시한다. 선 그래프는 실제 순서·시간 의미가 있는 경우에 쓴다. 3D, 의미 없는 원형, 과도한 도넛·레이더, 설명 없는 이중축은 사용하지 않는다.

차트 축·범례·툴팁에 단위를 일관되게 넣는다. 특정 막대만 강조할 때도 다른 값이 읽혀야 한다. 발표 핵심이 hover tooltip에만 나타나면 안 된다.

### 8.2 렌더링

차트 전용 부모 컨테이너에 명시적인 너비·높이를 주고 `position: relative`를 사용한다. 고정 논리 캔버스 안에서 `responsive: true`, `maintainAspectRatio: false`를 사용할 수 있다. 기본 폰트는 Pretendard로 지정하고 축·범례의 크기는 위 토큰을 따른다. [R04]

`animation: false`를 기본으로 하며 export/QA에서 애니메이션을 강제로 끈다. 화면에서 숨겨진 슬라이드의 0×0 부모 크기로 초기화하지 않는다. 슬라이드 표시 후 resize/update와 실제 그리기 완료를 기다린다.

렌더링 DPR은 export에서 보통 2로 고정하고 다른 값이 필요하면 크기·메모리 영향을 기록한다. 차트는 canvas이므로 PDF/PPTX에서 자동 벡터 그래프가 된다고 주장하지 않는다. 이미지 변환은 해당 크기에서 실제 가독성을 검증한다.

폰트는 차트 생성 전에 로딩하고, 폰트가 뒤늦게 로드되면 차트를 갱신한다. print에서는 화면의 레이아웃에 의존하지 말고 명시적인 chart resize 또는 검증된 정적 snapshot을 사용한다. PDF 인쇄 이벤트만 믿고 즉시 캡처하지 않는다. [R04, R05]

### 8.3 접근성과 자료 보존

각 차트에 의미 있는 텍스트 설명과 동등한 데이터 표를 제공한다. 표는 읽기 버전에서 제공해도 되지만 핵심 값·결론은 슬라이드에서 직접 읽혀야 한다. 캔버스 DOM bounds 검사는 축 라벨 내부 잘림을 찾지 못하므로 차트 스크린샷도 직접 확인한다.

같은 데이터로 HTML 차트·PDF·PPTX·대본의 수치가 일치해야 한다. 테스트용 synthetic chart는 실제 수업 자료가 아니며 테스트 fixture에서만 사용한다.

## 9. KaTeX·Mermaid·코드

KaTeX는 필요한 수식만 렌더링하고, 표현하지 못하는 수식 오류를 조용히 숨기지 않는다. 수식은 무엇을 계산하는지, 기호, 출발 가정, 단계, 간단한 예시, 결과와 연결을 대본에 설명한다. 적용되지 않는 항목을 억지로 채우지 않는다. [R09]

간단한 과정은 HTML/SVG 컴포넌트로 그려도 된다. 복잡한 구조만 Mermaid를 사용하고, 공통 폰트·색·여백을 적용한 SVG를 만든다. 폰트를 먼저 로딩하고 잘린 라벨을 확인한다. 기본 보안 수준은 `strict`로 유지하며, 외부 입력의 클릭 명령·raw HTML을 허용하지 않는다. [R10]

Prism.js는 필요한 언어만 포함하고 배경·대비를 흑백 디자인에 맞춘다. 사용자에게 보여줄 코드와 에이전트가 실행할 코드를 구분한다. 예제 안의 API 키는 명백한 자리표시자로 쓰며 실제 토큰·실행 경로를 노출하지 않는다. [R11]

긴 프롬프트는 화면에 중요한 부분만 표시하고 전체 예시는 승인된 읽기자료에 둔다. 긴 줄을 글자 크기 축소로 처리하지 말고 의미 단위로 줄바꿈한다.

## 10. 사실 확인·최신성

원본 자료의 핵심 주장·조건·수치·한계를 유지한다. 자료가 여러 개인 경우 의견 일치·차이를 임의로 하나의 확정된 사실로 합치지 않는다. 설명자의 해석·추천은 조건을 밝힌다.

모델명, 요금제, 지역별 가격, 세금, API 가격, 구독과 API의 관계, 사용량 제한, 포함 기능, 지원 플랫폼, 현재 트렌드는 강의 제작 시 공식 자료에서 확인한다. 모델의 사전지식이나 이전 대화의 수치만으로 작성하지 않는다.

시점 정보는 `sources.yaml`에 `checked_at`을 ISO 날짜로 기록한다. 가격·상품 비교 슬라이드에는 화면에도 확인일을 넣는다. 발표 72시간 전 재확인을 운영 기준으로 삼되, 그 기간을 법칙이나 최신성 보장으로 표현하지 않는다.

공식 문서에 없는 정확한 사용량 한도, 계정별 실험 기능, 지역 제한은 확인되지 않았다고 기록한다. 웹에 접근하지 못해도 변하지 않는 개념과 기획 작업은 진행할 수 있으나 해당 주장을 공개 가능한 확정 사실로 만들지 않는다.

핵심 주장마다 source ID를 연결하고 원본 페이지/section을 기록한다. 공개 source registry에는 필요한 링크와 짧은 설명만 넣고 원문을 대량 복제하지 않는다.

## 11. 발표 원고

발표 원고는 요약문이나 번역문이 아니라 실제로 읽으며 가리킬 수 있는 한국어 원고다. `deck.json`의 slide ID에 연결하며 DOCX와 발표자 화면이 같은 데이터를 사용한다.

필요한 항목만 선택한다.

1. 먼저 알아야 할 배경지식.
2. 실제 말할 자연스러운 발표 원고.
3. 처음 가리킬 곳과 Figure/Chart의 시선 이동 순서.
4. 축·범례·색·화살표·박스의 의미.
5. 수식의 기호·가정·도출 단계·간단한 숫자 예시.
6. 알고리즘의 입력·반복·조건·평가 기준·출력.
7. 헷갈릴 점, 의미와 한계, 다음 슬라이드 연결 문장.

모든 장에서 11개 항목을 기계적으로 출력하지 않는다. 다만 실제 말할 원고와 다음 장으로 연결하는 문장은 본편에서 기본 제공한다. 마지막 장의 연결 문장은 종료 안내로 대체한다.

DOCX는 슬라이드 번호·제목·작은 썸네일(가능한 경우)·목표 시간·실제 원고·학습용 보충 설명·출처 순으로 구성한다. ‘읽지 않아도 되는 공부용 설명’과 ‘발표 시간에 포함되는 말’이 시각적으로 구분되어야 한다.

예상 발표 시간은 슬라이드별 `durationSec` 합계와 실제 원고 길이 기반의 거친 추정을 함께 검토한다. 한국어 말하기 속도는 발표자·용어에 따라 달라지므로 고정 수치 하나로 발표 시간을 보증하지 않는다. 최종 시간은 리허설로 확인할 항목으로 남긴다.

## 12. 동아리 수업의 톤과 실제 경험

가볍고 유쾌하되 개념의 정확성을 희생하지 않는다. 자조적·상황형 한 줄 비유나 직접 만든 밈은 허용한다. 밈은 대략 8–10장당 1개 이하를 기본 상한으로 하되 반드시 넣을 필요는 없다. 타인을 조롱하거나 특정 구독을 압박하는 표현은 피한다.

‘월 구독료가 술자리 한 번 정도’ 같은 비유는 현재 가격과 무관한 교육적 비교일 수 있음을 밝힌다. 월 3만 원을 최신 가격처럼 확정하지 않고, 술을 마시지 않는 학생도 이해할 수 있게 선택 가능한 지출 예시로 한정한다.

사용자 경험은 문제 → 사용자가 내린 판단 → AI에 맡긴 부분 → 직접 검증한 부분 → 배운 점으로 구성한다. ‘AI가 모두 알아서 했고 나는 아무것도 하지 않았다’ 또는 ‘모든 코드를 직접 작성했다’로 왜곡하지 않는다.

MediFlow에서는 Copilot으로 Colab 학습 코드 자동화와 웹 대시보드를 만든 경험, 작업에 맞는 모델 선택과 토큰 관리의 필요성을 설명할 수 있다. 로컬 LLM 실험 도구는 사용자가 파라미터와 결과를 직접 확인하며 이해하기 위해 만든 도구라는 맥락을 보존한다. 공개 여부와 실제 구현 증거는 별도 확인한다.

실습 시간, 의무 과제, 출석·성과 평가는 새로 만들지 않는다. 수업 후 선택적으로 시도할 작은 예시는 제안할 수 있지만 제출 의무가 있는 활동으로 표현하지 않는다.

## 13. 내보내기와 공개 경계

HTML이 시각 원본이다. PPTX는 기본 `visual` 모드라는 한계를 파일명·README·최종 보고에 표시한다. PDF·PPTX를 만들었다면 각각의 마지막 결과를 확인한다. HTML에서 잘 보였다는 이유로 export QA를 생략하지 않는다.

사이트의 발표자 원고는 private 검토용 빌드에만 포함한다. 공개 HTML에는 CSS로 감춘 원고, 숨겨진 JSON, source map, private 이미지, 토큰을 넣지 않는다. 저장소가 public이면 추적된 `deck.json`의 일반 원고도 공개될 수 있다. 이를 숨겨야 하는 요구가 있으면 private 저장소를 유지하거나 별도 공개 대상 구성이 필요하며, 사이트에서 숨기는 것만으로 해결됐다고 보고하지 않는다. 공개할 읽기자료가 필요하면 승인된 내용만 별도로 생성한다.

PDF의 물리 크기는 13⅓×7½인치로 고정하고 화면용 transform과 인쇄용 transform을 분리한다. 예를 들어 인쇄 wrapper를 1280×720 CSS px로 두고 1920×1080 논리 slide를 2/3 비율로 넣으면 96 CSS px/in 기준에서 이 페이지 크기에 맞는다. `@page` margin은 0, slide당 wrapper 하나, 마지막 장을 제외한 page break를 명시한다. 화면에서 비활성인 slide도 export에서는 렌더링하고, Chart.js의 준비 완료를 기다린다. Playwright PDF 호출은 CSS page size와 background 설정을 확인해 구현한다. [R13]

인쇄 scaling은 wrapper·브라우저 PDF 옵션에서 중복 적용하지 않는다. 실제 PDF의 페이지 박스와 첫/마지막 slide를 검사해 16:9가 유지되는지 검증한다.

재생을 위한 서버는 로컬 HTTP의 간단한 정적 서버로 충분하다. `file://` 더블클릭에서 모듈·fetch가 언제나 작동한다고 보장하지 않는다. 발표용 폴더를 복사한 다음에도 로컬 명령 하나로 실행하는 경로를 문서화한다.

## 14. 완료 기준

실제 브라우저에서 모든 장을 확인하고, 폰트·overflow·이미지·차트·표·수식·출처·대본 매핑·시간·내보내기를 검사한다. 자동 검사로 확인할 수 없는 디자인 완성도나 강의 이해도는 검수자가 직접 보고 판단할 항목으로 표시한다.

문제를 수정한 후 영향을 받은 슬라이드와 대표 레이아웃을 다시 검사한다. 상세 검사 항목과 증거 형식은 `docs/QA_AND_ACCEPTANCE.md`를 따른다.
